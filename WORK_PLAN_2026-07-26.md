## 1. 📱 UI Mobile — Opzioni di Selezione Nascoste

### Problema

In modalità smartphone (< 768px), la toolbar superiore comprime tutti i controlli orizzontalmente. Quando `selectMode` è attivo, i pulsanti **All**, **None** e il **contatore pagine selezionate** competono con:
- Pulsanti layout (4)
- Zoom/rotazione (fuori griglia)
- Select toggle
- Navigatore pagine

Anche dopo il fix responsive (`#40ca5f4`), su schermi ≤ 375px la toolbar trabocca e i controlli di selezione finiscono fuori vista senza che l'utente sappia che esistono.

### Possibili Soluzioni

#### A. Bottom Sheet per Selezione (consigliata)
- Quando `selectMode` è attivo su mobile, mostrare un **bottom sheet** dedicato con:
  - Contatore: "3 selezionate"
  - Pulsanti: `All` | `None` | `Done`
  - Il bottom sheet si chiude al tap su `Done` (che disattiva selectMode)
- Vantaggio: non compete con la toolbar, sempre visibile, pattern mobile nativo
- Riferimento: già implementato pattern bottom sheet per TOC su mobile

#### B. Toolbar a Due Righe su Mobile
- Su mobile, splittare la toolbar in due righe:
  - Riga 1: layout + zoom + navigazione
  - Riga 2 (visibile solo in selectMode): Select toggle + counter + All + None
- Svantaggio: occupa più spazio verticale, già scarso su mobile

#### C. Floating Action Button (FAB) per Selezione
- Sostituire il toggle Select nella toolbar con un FAB in basso a destra
- Al tap, espande un radial menu con All / None / Done
- Svantaggio: pattern meno scopribile

### File Coinvolti
- `src/components/UnifiedViewer.tsx` — toolbar rendering
- `src/App.tsx` — gestione stato `selectMode`
- `src/components/BottomToolbar.tsx` — eventuale estensione/riutilizzo

### Criteri di Successo
- Su viewport 375px, tutti i controlli di selezione sono accessibili **senza scroll orizzontale**
- Il flusso "apri selezione → seleziona tutto → deseleziona → chiudi" è completabile in ≤ 3 tap
- Il bottom sheet non si sovrappone al contenuto in modo problematico

## 2. 🐢 Rendering Lento per PDF con Molte Pagine

### Problema

Con `modern.pdf` (819 pagine), il rendering iniziale e i cambi di layout/scala sono lenti perché:

1. **Pool canvas troppo piccolo**: `POOL_SIZE = 12` canvas in `PageView`. Per griglie a 5 colonne, solo ~2.5 righe sono coperte dal pool; lo scrolling rivela aree non renderizzate.

2. **Grid view senza pool**: `GridView` non ha pool canvas — ogni `GridCanvas` è un componente React indipendente con il suo canvas. Quando la griglia ha 819 celle, React monta 819 componenti canvas, causando:
   - DOM enorme (819 `<canvas>` elementi)
   - Overhead di React reconciliation su ogni resize
   - Nessuna condivisione di canvas tra celle

3. **Rendering sul thread principale**: `renderPageToCanvas` esegue `page.render()` sul main thread. Per 819 pagine in grid mode, tutte le pagine visibili competono per la CPU.

4. **Ricostruzione del pool ad ogni cambio scala**: Quando lo zoom cambia, `PageView` distrugge tutti i canvas (`poolRef.current.forEach(c => c.remove())`) e li ricrea. I canvas già renderizzati alla vecchia scala vengono buttati via.

### Possibili Soluzioni

#### A. Virtual Scrolling per GridView (consigliata)
- Invece di renderizzare tutte le 819 celle, usare un **virtual scrolling** che monta solo le celle visibili + buffer
- Librerie: `@tanstack/react-virtual` (già nel bundle? verificare)
- Implementazione custom: calcolare `startRow`/`endRow` basati su `scrollTop` e renderizzare solo `(endRow - startRow + buffer) * cols` elementi
- Vantaggio: DOM ridotto a ~50-100 nodi invece di 819

#### B. Pool Canvas per GridView
- Estendere il pattern pool di `PageView` anche a `GridView`
- Pool di ~20 canvas condivisi, assegnati dinamicamente alle celle visibili
- Riciclare canvas fuori dal viewport

#### C. OffscreenCanvas / Web Worker (avanzato)
- Usare `OffscreenCanvas` + Web Worker per renderizzare le pagine fuori dal main thread
- pdf.js supporta `OffscreenCanvas` dalla v3
- Vantaggio: UI reattiva durante il rendering, nessun frame drop
- Svantaggio: complessità implementativa alta, compatibilità browser (Safari supporta OffscreenCanvas dalla 16.4)

#### D. Render Prioritization / Lazy Loading
- Dare priorità alle pagine visibili al centro del viewport
- Usare `requestIdleCallback` o scheduler per pagine fuori viewport
- Mostrare placeholder (rettangolo grigio con numero pagina) mentre la pagina è in coda di render

### File Coinvolti
- `src/components/UnifiedViewer.tsx` — `GridView`, `GridCanvas`, `PageView`, `POOL_SIZE`
- `src/lib/pdfRenderer.ts` — `renderPageToCanvas` (eventuale supporto OffscreenCanvas)
- Nuovo file: `src/hooks/useVirtualScroll.ts` o `src/lib/canvasPool.ts`

### Criteri di Successo
- Grid 5 colonne su modern.pdf (819 pp.): **tempo di primo render < 3 secondi**
- Scroll fluido (60fps percepiti) senza blank canvas visibili
- DOM node count in grid mode: < 200 nodi (vs 819 attuali)

## 3. 🗑️ Cache Canvas Evicta allo Scroll

### Problema

Quando l'utente scrolla, le pagine che escono dal viewport perdono il loro canvas renderizzato:

- **PageView**: il pool di 12 canvas è FIFO — i canvas fuori dal viewport vengono riassegnati a nuove pagine. Quando l'utente torna indietro, la pagina deve essere **ri-renderizzata da zero**.
- **GridView**: ogni `GridCanvas` è un componente React. Quando esce dal viewport (con virtual scrolling futuro), viene **smontato completamente**, perdendo il bitmap. Al re-mount, `lastRenderedRef` viene resettato (nuova istanza del componente), quindi il canvas viene ri-renderizzato anche se `pageNumber` e `scale` sono identici.

### Possibili Soluzioni

#### A. Cache dei Bitmap con `OffscreenCanvas` o `ImageBitmap`
- Dopo aver renderizzato una pagina su canvas, salvare il risultato come `ImageBitmap` (o in un `OffscreenCanvas`)
- La cache è una `Map<number, ImageBitmap>` indicizzata per `pageNumber`
- Quando una pagina torna visibile, invece di chiamare `page.render()`, si disegna l'`ImageBitmap` sul canvas con `ctx.drawImage(bitmap, 0, 0)`
- **Limite cache**: LRU con capienza massima (es. 50 bitmap)
- Invalida la cache solo quando `scale` o `rotation` cambiano
- Vantaggio: `drawImage` di un bitmap è quasi istantaneo rispetto a `page.render()`

#### B. Aumentare il Pool e usare Strategia LRU
- Aumentare `POOL_SIZE` da 12 a 30-40
- Invece di distruggere canvas fuori viewport, tenerli in una coda LRU
- Solo quando il pool è pieno, il canvas meno recente viene riciclato
- Il canvas mantiene il riferimento `__page` per evitare re-render se la stessa pagina torna visibile

#### C. Cache delle Dimensioni Pagina (già implementato ✅)
- `pageDimsCache` in `pdfRenderer.ts` già cachea le dimensioni
- Estensione: cacheare anche il viewport per scala, per evitare `page.getViewport({scale})` ripetuto

#### D. Persistent Canvas per GridView
- Invece di smontare i `GridCanvas` fuori viewport, usare `visibility: hidden` o `display: none` mantenendo il DOM
- Combinato con virtual scrolling: mantenere un buffer di canvas "nascosti" pronti al riutilizzo
- Il componente `GridCanvas` rimane montato e il suo `lastRenderedRef` sopravvive

### File Coinvolti
- `src/components/UnifiedViewer.tsx` — `PageView` pool, `GridCanvas`
- `src/lib/pdfRenderer.ts` — nuova cache bitmap, `renderPageToCanvas`
- Nuovo file: `src/lib/bitmapCache.ts`

### Criteri di Successo
- Scroll avanti e indietro su un PDF di 819 pagine: **nessuna pagina visibile è mai bianca/placeholder** dopo il primo render
- Hit rate della cache bitmap > 80% durante scroll tipico
- Memoria: cache limitata a ~50 bitmap (circa 50 × 1MB per pagina A4 @300dpi = 50MB max, accettabile)
